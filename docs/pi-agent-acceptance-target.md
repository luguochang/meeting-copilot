# Pi 实时教练 Agent 验收目标

## 本轮目标

验证用户能在真实工作台中看见一条完整的 Agent 闭环：稳定转写进入后，Pi 使用场景技能包完成检查，必要时给出一条带原文证据的可执行建议；不需要打断时明确显示静默原因。验收同时记录录音状态、运行时、Agent turn、工具调用、历史检索和决策延迟。

## 可量化门禁

- 每个干预必须带至少一个 `evidence_segment_id`，目标通过率 100%。证据原文由 Pi bridge 和 Python 侧共同校验，不能引用不存在或改写的文本。
- 每个静默结果必须带 `decision_reason`，目标通过率 100%。页面要区分“Pi 正在工作但选择静默”和“没有录音/没有触发”。
- 同一会议中相同事件和证据不得重复出现，目标重复数为 0。历史建议保留在列表中，但当前卡片只突出最新有效建议。
- 决策延迟分两级：产品目标 P95 <= 5 秒，硬上限 <= 10 秒。超过目标要进入性能问题清单，不能继续宣称实时低延迟。
- Pi 请求成功时 `runtime_used=pi` 且无 fallback；Pi 失败时必须可见地标识 fallback 或静默保护，不能伪装成已监听。

## 真实音频验收（2026-08-18）

本次使用系统麦克风 `Microphone (K66)` 采集真实环境声音，未播放或外放测试音频；音频通过工作台同一条 `/live/asr/stream/ws/{meeting_id}` 实时 PCM 入口进入当前会议。

- 录音状态：`microphone / epoch-3 / ready`，时长 19.8 秒，4 个音频块，316,800 个采样，音频文件已正确封存。
- ASR 链路：收到 `asr_ready`，产生 2 个最终段落；页面显示“那场跨年的烟火绽放天空。”和“我曾经走过多远。”，另有 1 个段落等待校对。
- Pi 链路：新音频批次触发 1 个成功的 intelligence job，`runtime_requested=pi`、`runtime_used=pi`、无 fallback；1 轮 Agent、1 次 `keep_silent`、7 项检查、延迟 3.52 秒、复用已有 Session。
- Agent 决策：新麦克风内容与当前 onboarding 访谈目标无关，Pi 明确选择静默，不重复之前的追问；旧建议仍保留并继续显示其原文依据。
- 页面交互：左侧从 1 段增加到 3 段确认/校对内容，右侧显示运行摘要和“本轮结论：暂不打断……”，历史建议数量保持可见。
- 结束时客户端测试脚本收到服务端主动关闭连接（`ConnectionResetError`），但录音已封存、最终转写已落库、Pi job 已成功；归类为结束握手清理问题，不是音频或 Agent 失败。

这次验证通过了“真实系统音频 -> ASR -> Pi Agent -> 页面投影”的后端和前端投影链路；浏览器 `getUserMedia` 权限仍被拒绝，因此浏览器自身的麦克风授权入口还未通过独立验收。

## 本轮体验优化

- 右侧运行摘要新增 Agent 轮数和工具调用数，用户可以看到 Pi 实际完成了哪些动作。
- 当已有建议卡片存在时，仍展示最新 Pi 静默结论，明确说明它为什么没有重复打断。
- 评估脚本新增证据覆盖率、静默原因覆盖率和重复干预计数，避免只凭“右侧出现过卡片”判断 Agent 质量。

## 真实音频复验与问题修复（2026-08-18）

第二轮真实麦克风采集暴露了一个比“Pi 是否启动”更关键的问题：Pi 在 9.85 秒后给出 `intervention`，但唯一证据仍是上一轮的 `system_audio:e1:interview-vague-2`，没有引用本轮新增的麦克风段落；页面因此新增了一条与旧建议重复的追问。这说明原有证据校验只保证“证据存在”，没有保证“证据属于本轮触发”。

已在 Python Host 侧增加证据新鲜度门禁：

- intervention 必须至少引用一个本轮 `new_paragraphs`；允许同时引用历史段落，用于跨轮冲突判断。
- 只有旧证据的干预会被抑制为 silent，记录 `intervention_suppressed=true`、`suppression_reason=stale_evidence`，并把原因投影到页面。
- 静默事件不会清空最近一条仍有效的正式建议；当前结论与建议历史分开显示。

门禁已有 2 个 Pi 单测覆盖：旧上下文独立证据会被抑制，新证据与历史证据组合可以正常干预。

修复后的第三轮真实麦克风采集（`epoch-6`）未播放或外放任何测试音频：

- 录音状态：`microphone / epoch-6 / ready`，约 20.1 秒，后端落库 321,600 个采样；K66 原始输入 20 秒内 64/67 个块有明显能量。
- ASR 链路：收到 `asr_ready` 和最终段落，页面正文从 3 段变为 4 段；新增段落带 `microphone:e6` 证据标识。
- Pi 链路：`job_23a4b00a761b7fa5fae32bac` 成功，`runtime_used=pi`、无 fallback；1 轮 Agent、1 次工具调用、7 项检查、约 3.93 秒、复用会议上下文。
- Agent 决策：Pi 识别新增内容无法可靠关联 onboarding 访谈目标，选择静默并说明“避免把可能的 ASR 误识别当作用户立场”。这轮没有新增重复建议，历史数量保持为 3。
- 页面截图：`artifacts/tmp/pi-real-provider-acceptance-data-20260818/pi-coach-epoch6-coach-panel.png`，可看到运行摘要、本轮静默结论、保留的当前建议和历史建议。

本轮证明了“真实麦克风 -> FunASR -> Pi Agent loop -> 有理由静默 -> 页面保留上下文”的闭环；epoch-7 进一步证明了真实新证据可以触发一条带证据的新干预，但该干预的最终价值仍受 ASR 噪声和后续静默判断影响。

## 真实新证据干预验收（epoch-7）

继续使用 `Microphone (K66)` 采集真实环境声音，未播放、外放或注入预置音频。录音状态为 `microphone / epoch-7 / ready`，时长 25.2 秒，落库 403,200 个采样；FunASR 形成 3 个 `microphone:e7` 最终段落。实际转写存在明显语义漂移，因此这轮同时检验了“Agent 能否识别跑题”和“是否会把 ASR 噪声误当成业务事实”。

- 正向干预 job：`job_5c8eaeb0f346e5e0e334ee4e`，`runtime_used=pi`、无 fallback，1 轮 Agent、1 次 `submit_intervention`、7 项检查、延迟 8.47 秒。
- 新鲜证据：follow-up 引用了 `microphone:e7:vad_endpoint_006`，并组合 `e4/e6` 历史段落判断连续语义漂移；满足“至少一个本轮新证据”的 Host 门禁。
- 页面建议：标题“拉回访谈主线”，可直接说出“请先停一下并明确转场：回到 onboarding，能讲一个最近实际卡住的步骤吗？”。当前卡片展示理由与原文依据，历史建议从 3 条增加到 4 条并支持展开全部。
- 建议价值：具体、可立即执行，并且不是把旧追问简单换一种说法；价值评为“中等偏高”。扣分点是新证据本身疑似 ASR 噪声，建议更适合作为低打扰的“确认转场”，不应升级为高紧急度业务判断。
- 后续静默 job：`job_07336b2104bb1dea161eb172` 基于后续 `microphone:e7:vad_endpoint_008` 判断内容可能是自言自语或识别噪声，选择静默；页面保留上一条有效卡片并同时展示最新静默原因。
- 页面截图：`artifacts/tmp/pi-real-provider-acceptance-data-20260818/pi-coach-epoch7-fresh-intervention.png`。

修复后的 3 个成功 Pi job 中，1 次干预、2 次静默，job 级触发率为 33.3%；按真实录音批次计，`epoch-6/7` 中 1 个批次产生过干预，批次触发率为 50%。延迟分别约 3.93、8.47、10.74 秒，均值约 7.72 秒，样本 P95 约 10.74 秒。正向干预在 10 秒硬上限内，但最终静默 job 超过硬上限，当前仍不能宣称整体实时延迟达标。

已确认的失败或风险：

- `epoch-7` 最新静默轮为 10.74 秒，超过 10 秒硬上限；Pi 的 `decision_latency_budget_ms=10000` 与实际完成状态不一致，需要在 Host 侧增加真正的 deadline/cancel 或更小上下文预算。
- 多个 correction job 因 `V2TranscriptRevisionConflict` 失败；本轮最终转写和 Agent job 仍成功，但校对冲突会降低新证据质量。
- 中间干预与后续“疑似噪声”静默同时可见，虽然没有覆盖历史，但当前卡片缺少“已被后续证据降级”的状态。后续应增加 Agent `retract/deprioritize` 决策，避免保留可信度已经下降的建议。
